# CryptoCore

CryptoCore — минималистический консольный криптографический провайдер для
шифрования и расшифрования файлов с помощью AES-128, а также вычисления
SHA-256, SHA3-256, HMAC-SHA256, AES-CMAC и получения ключей из паролей.
Реализованы первые семь спринтов,
включая бонусные требования пятого спринта к CMAC.
Дополнительно внесены замечания преподавателя к третьему спринту:
аутентифицированные форматы, защищённые ключевые файлы и контроль CTR.

> **Предупреждение о безопасности:** режим ECB раскрывает повторяющиеся шаблоны
> открытого текста и не подходит для защиты реальных данных. В этом проекте он
> реализован исключительно как учебная основа для более безопасных режимов из
> следующих спринтов.

Учебная реализация не проходила независимый аудит и не гарантирует
constant-time выполнение Python. Для промышленной защиты данных используйте
проверенные криптографические библиотеки.

## Требования

- Python 3.9 или новее;
- `pip`;
- [PyCryptodome](https://pycryptodome.readthedocs.io/) версии 3.20 или новее.

PyCryptodome предоставляет проверенный блочный примитив AES. CryptoCore
самостоятельно реализует логику режимов, GHASH для GCM, HMAC-SHA256,
AES-CMAC, PBKDF2-HMAC-SHA256, иерархию ключей и PKCS#7.

## Использование

Для шифрования ключ передаётся в виде ровно 32 шестнадцатеричных символов — это 16 байт,
необходимые для AES-128. При шифровании `--key` можно не указывать: CryptoCore
сгенерирует ключ системным CSPRNG и один раз выведет его в `stdout`.

Шифрование файла:

```bash
cryptocore --algorithm aes --mode ecb --encrypt \
  --key 000102030405060708090a0b0c0d0e0f \
  --input plaintext.txt --output ciphertext.bin
```

Шифрование с автоматической генерацией ключа:

```bash
cryptocore --algorithm aes --mode ctr --encrypt \
  --input plaintext.txt --output ciphertext.bin
# [ИНФО] Сгенерирован случайный ключ: <32 hex-символа>
```

Сохраните показанный ключ: он намеренно не записывается в файл с шифротекстом.
Без него расшифрование невозможно. Для расшифрования обязательно указать
`--key` либо `--key-file`. При ключе из одинаковых или последовательных байтов программа
выводит предупреждение в `stderr`.

Расшифрование файла:

```bash
cryptocore --algorithm aes --mode ecb --decrypt \
  --key 000102030405060708090a0b0c0d0e0f \
  --input ciphertext.bin --output decrypted.txt
```

Параметры `--algorithm aes`, `--mode` и `--input` обязательны.
Также необходимо указать ровно один из флагов: `--encrypt` или `--decrypt`.
Если параметр `--output` отсутствует, CryptoCore добавляет к имени входного
файла расширение `.enc` при шифровании или `.dec` при расшифровании.

Ошибки аргументов, файловой системы и криптографических операций выводятся в
стандартный поток ошибок. При ошибке программа завершается с ненулевым кодом.

## Аутентифицированное шифрование и ключевые файлы

Для новых файлов доступны `gcm`, `etm`, `cbc-hmac` и `ctr-hmac`. При неверном ключе,
AAD или изменении данных команда возвращает общую ошибку аутентификации.
Проверка тега предшествует расшифрованию: выходной файл не создаётся, а
существующий файл не изменяется при отказе.

Пример GCM с новым ключом в отдельном защищённом файле:

```powershell
cryptocore --algorithm aes --mode gcm --encrypt --input document.pdf --output document.gcm --save-key document.key --aad aabb
cryptocore --algorithm aes --mode gcm --decrypt --input document.gcm --output restored.pdf --key-file document.key --aad aabb
```

`--save-key` разрешён только при генерации нового ключа во время шифрования.
Файл содержит 32 hex-символа и перевод строки; существующие файлы и ссылки
не перезаписываются. В этом случае ключ не выводится в stdout. Без этой
опции вывод нового ключа остаётся прежним.

В Linux/WSL файл создаётся с правами **0600**. На Windows до записи ключа
отключается наследование ACL и доступ предоставляется только текущему
пользователю через `icacls`; при отказе ограничения прав ключ не записывается.
При чтении в Linux отклоняются ключевые файлы с доступом для группы/остальных
пользователей. Символические ссылки отклоняются. Для самостоятельно созданных
ключевых файлов Windows ограничение ACL следует установить отдельно.
Ключевой файл нельзя перезаписать выходным файлом шифрования, включая жёсткие
ссылки. `*.key` исключены из Git.

`--key` и `--key-file` взаимоисключающие. Файловая передача позволяет не
размещать ключ в аргументах процесса и истории команд. Для работы без вывода
ключа используйте `--save-key`, затем `--key-file`.

| Режим | Формат файла |
| --- | --- |
| `gcm` | `nonce (12 байт) ∥ ciphertext ∥ tag (16 байт)` |
| `etm` | `CETM\x01 ∥ режим (1 байт) ∥ IV (16 байт) ∥ длина шифротекста (8 байт) ∥ ciphertext ∥ HMAC (32 байта)` |
| `cbc-hmac` | `CCBC\x01 ∥ IV (16 байт) ∥ ciphertext ∥ HMAC (32 байта)` |
| `ctr-hmac` | `CCTR\x01 ∥ размер сегмента (4 байта) ∥ длина данных (8 байт) ∥ HMAC заголовка (32 байта) ∥ сегменты` |

GCM реализован по [NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf).
CBC-HMAC и CTR-HMAC используют собственные версионированные форматы.
Разные ключи AES и MAC выводятся из основного ключа через HMAC-SHA256 с
метками назначения и формата. В этих двух форматах каждый MAC включает длину AAD и сами AAD.
CBC-HMAC аутентифицирует версию, IV и шифротекст до CBC и проверки padding.

В CTR-HMAC сегмент состоит из nonce (12 байт), шифротекста и HMAC (32 байта).
Тег связывает заголовок, номер сегмента, nonce и шифротекст: перестановка,
усечение и дописывание сегментов обнаруживаются. Все теги проверяются до
расшифрования. Целые числа в заголовке записываются big-endian.

`--aad` принимает hex-строку и разрешён только для аутентифицированных
режимов (`gcm`, `etm`, `cbc-hmac`, `ctr-hmac`). Он не записывается в файл; при расшифровании нужно повторить то же
значение. Для GCM-файла без заголовка можно передать nonce через `--nonce`
либо `--iv` при расшифровании; файл должен включать тег. При шифровании
nonce/IV всегда генерируется автоматически.

В CTR-HMAC 96-битный nonce отделён от 32-битного счётчика, начинающегося с
нуля для каждого сегмента. Nonce обновляется каждый 1 МиБ по умолчанию;
допустимый размер сегмента — от 1 байта до 64 МиБ:

```powershell
cryptocore --algorithm aes --mode ctr-hmac --encrypt --input archive.zip --output archive.ctr --save-key archive.key --ctr-segment-size 1048576
cryptocore --algorithm aes --mode ctr-hmac --decrypt --input archive.ctr --output restored.zip --key-file archive.key
```

Все nonce создаются CSPRNG. В CTR-HMAC повтор внутри файла приводит к повторной генерации
и отказу после восьми неудачных попыток. Предел счётчика проверяется заранее.
Между файлами уникальность случайных nonce вероятностная; для больших серий
операций необходимо также менять ключи. Для GCM используйте отдельный ключ,
который не используется в других режимах; nonce не должен повторяться с ним.

Старые форматы сохраняются для совместимости. В старом CTR теперь запрещено
числовое переполнение счётчика. Переход на `ctr-hmac` требует повторного
шифрования исходного файла.

PKCS#7 проверяет все 16 байтов последнего блока без ранних выходов по содержимому.
**Строгое constant-time исполнение Python не гарантируется.** Обычный CBC без
MAC не защищён от padding oracle; защиту обеспечивает `cbc-hmac` с проверкой
MAC до CBC и unpad. Тесты проверяют этот порядок, а не доказывают отсутствие
всех побочных каналов интерпретатора.

Ротация nonce ограничивает использование счётчика. GCM, хеширование и HMAC
обрабатывают файл по частям с постоянным потреблением памяти. Старые режимы,
`cbc-hmac`, `ctr-hmac` и общий `etm` пока загружают сам файл сообщения целиком;
большой AAD в `gcm` и `etm` обрабатывается потоково через `--aad-file`.

## AEAD и потоковый GCM (спринт 6)

AEAD объединяет конфиденциальность сообщения и проверку его подлинности.
Associated Data (AAD) — дополнительные данные, которые аутентифицируются,
но не шифруются: например, идентификатор сообщения, версия протокола или
метаданные файла. В этой утилите AAD не включается в выходной файл, поэтому
при расшифровании нужно предоставить те же байты отдельно.

GCM самостоятельно реализует CTR и GHASH по NIST SP 800-38D. Для GHASH
используется поле `GF(2^128)` с полиномом `x^128 + x^7 + x^2 + x + 1`.
Таблица из 256 значений для фиксированного H ускоряет умножение: вместо
128 побитовых шагов выполняются 16 шагов по байтам. Это учебная оптимизация,
а не гарантия отсутствия побочных каналов.

CLI при каждом шифровании создаёт случайный nonce длиной 12 байт через
CSPRNG и сохраняет его в начале файла. Тег имеет полную длину 16 байт:

```text
nonce (12 байт) || ciphertext (длина исходного сообщения) || tag (16 байт)
```

Формат GCM совместим с версией 0.4.1: ранее созданные файлы не нужно
перешифровывать. Пустой файл тоже допустим; его GCM-представление занимает
28 байт. Padding не применяется.

### AAD в hex или отдельном бинарном файле

```powershell
cryptocore --algorithm aes --mode gcm --encrypt --input message.txt --output message.gcm --save-key message.key --aad aabbccddeeff
cryptocore --algorithm aes --mode gcm --decrypt --input message.gcm --output restored.txt --key-file message.key --aad aabbccddeeff
```

Для больших метаданных используйте `--aad-file`:

```powershell
cryptocore --algorithm aes --mode gcm --encrypt --input archive.zip --output archive.gcm --save-key archive.key --aad-file metadata.json
cryptocore --algorithm aes --mode gcm --decrypt --input archive.gcm --output restored.zip --key-file archive.key --aad-file metadata.json
```

`--aad-file` читает **сырые байты** файла, а не hex-строку. Изменение пробелов,
переводов строк или кодировки JSON меняет AAD и приводит к отказу проверки.
Этот параметр поддерживается только в `gcm` и `etm`, взаимоисключается с
`--aad` и читается фрагментами по 8192 байта. Если ни одна опция не указана,
AAD пуст. Выходной файл не может перезаписывать файл AAD, включая жёсткие ссылки.

Для внешнего GCM-файла без префикса nonce можно передать 24 hex-символа
через `--nonce` или совместимый `--iv`. Тогда вход содержит только
`ciphertext || tag`. При шифровании эти опции запрещены: nonce выбирает CSPRNG.

### Строгий отказ без открытого текста

Неверный ключ, корректно сформированный, но неверный AAD, изменение nonce,
шифротекста или тега приводят к коду `1` и общей ошибке:
`аутентификация не пройдена: неверный ключ, AAD или повреждённые данные`.
В stdout не выводится открытый текст, выходной файл не создаётся, а ранее
существовавший файл сохраняется. Неверный формат hex в `--aad` — ошибка
аргументов с кодом `2`, а не попытка аутентификации.

Расшифрование выполняется в два этапа. Сначала GHASH обрабатывает AAD и
шифротекст, а во временный снимок записывается **только шифротекст**.
После проверки полного тега через `compare_digest` начинается CTR-расшифрование
этого снимка. Вход не перечитывается: изменение источника между проверкой
и расшифрованием не подменяет проверенные байты. Результат сначала записывается
во временный файл рядом с назначением и публикуется атомарной заменой только
после успеха. При обычных ошибках временные файлы удаляются.

Память ограничена текущими фрагментами, а не размером сообщения или AAD.
Для расшифрования требуется временное место на диске под снимок шифротекста
и готовый результат. При аварийном завершении процесса временный файл рядом
с назначением может сохраниться; его нельзя считать опубликованным результатом.

Повтор nonce с одним ключом GCM может разрушить конфиденциальность и
аутентификацию. Случайная генерация не является глобальным учётом nonce между
запусками: не используйте один ключ бесконечно и соблюдайте ограничения NIST
на число операций. Максимальная длина сообщения на один nonce — `2^36 - 32`
байта; счётчики длины проверяются до переполнения. AAD ограничен стандартом
до `2^64 - 1` бит (для байтового ввода — `2^61 - 1` байт).

### Общая схема Encrypt-then-MAC

Новый режим `--mode etm` использует AES и HMAC-SHA256 пятого спринта:

```text
C = authenticated_header || E(K_e, plaintext)
T = HMAC-SHA256(K_m, C || AAD)
output = C || T
```

Ключи `K_e` и `K_m` различаются: они выводятся из основного AES-ключа через
HMAC-SHA256 с разными метками назначения и выбранного режима. Заголовок
включает версию формата, номер режима, IV и длину шифротекста. Длина
фиксирует границу между C и AAD; IV и заголовок также аутентифицируются.
Сначала проверяется MAC, только затем вызываются AES-расшифрование и unpad.

`--etm-mode` выбирает `ctr` (по умолчанию), `cbc`, `cfb`, `ofb` или учебный
`ecb`. При расшифровании укажите тот же базовый режим. ECB даже с MAC
раскрывает повторяющиеся блоки и не обеспечивает надлежащую конфиденциальность.

```powershell
cryptocore --algorithm aes --mode etm --etm-mode ctr --encrypt --input message.txt --output message.etm --save-key etm.key --aad aabb
cryptocore --algorithm aes --mode etm --etm-mode ctr --decrypt --input message.etm --output restored.txt --key-file etm.key --aad aabb
```

Общий EtM не меняет старые форматы `cbc-hmac`/`ctr-hmac`; эти режимы
сохраняют прежние заголовки, ротацию nonce и правила вычисления тегов.
AAD потоковый и в EtM, но само сообщение в этом интерфейсе пока хранится в памяти.

### Библиотечный интерфейс

```python
from cryptocore import GCM, EncryptThenMAC
from cryptocore.csprng import generate_random_bytes

key = generate_random_bytes(16)
gcm = GCM(key)
encrypted = gcm.encrypt(b"message", aad=b"metadata")
assert GCM(key).decrypt(encrypted, aad=b"metadata") == b"message"

etm_key = generate_random_bytes(16)
etm = EncryptThenMAC(etm_key, mode="ctr")
encrypted = etm.encrypt(b"message", aad=b"metadata")
assert etm.decrypt(encrypted, aad=b"metadata") == b"message"
```

`GCM.encrypt()` генерирует свежий 12-байтный nonce при каждом вызове и
возвращает его вместе с шифротекстом и тегом. Для фиксированных тестовых nonce
используйте `GCM(key, nonce=...)`: один экземпляр не позволяет повторное
шифрование с явно заданным nonce. Это не заменяет учёт nonce между экземплярами.
Низкоуровневые `encrypt_gcm`/`decrypt_gcm` сохраняют прежний контракт
`ciphertext || tag`, nonce передаётся отдельно; для nonce другой длины
используется GHASH по стандарту. CLI и файловые функции используют ровно 12 байт.

AAD в API может быть байтами, открытым бинарным потоком или одноразовым
итератором фрагментов. При каждой отдельной операции поток нужно открыть заново
либо перемотать. Для постоянного потребления памяти сообщения используйте
`process_gcm_file`, `encrypt_gcm_stream` и `decrypt_gcm_stream` из `cryptocore.aead`.
Для произвольных потоков очистка/откат принадлежит вызывающему коду;
гарантию атомарной публикации файла даёт `process_gcm_file`.

### Проверка спринта 6

```powershell
python -m unittest tests.test_aead tests.test_aead_cli tests.test_aead_large tests.test_gcm_openssl -v
```

Тесты включают опубликованные [примеры NIST AES-GCM](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Standards-and-Guidelines/documents/examples/AES_GCM.pdf),
пустые сообщения и AAD, произвольное разбиение потока, nonce разных длин,
подмену данных/тегов, отказ без вывода открытого текста, 1000 уникальных nonce
в API и CLI и все базовые режимы EtM. В Linux/WSL реальный AAD 8 МиБ
проверяется с доступными процессу дополнительными 4 МиБ: чтение целиком
вызывает `MemoryError`, потоковые GCM и EtM успешно совпадают с эталонами.

Команда `openssl enc` [не поддерживает GCM](https://docs.openssl.org/3.0/man1/openssl-enc/),
поэтому пример `openssl enc -aes-128-gcm` из задания неприменим.
Совместимость в обе стороны проверяется через OpenSSL EVP (`libcrypto`)
в `tests/test_gcm_openssl.py` и дополнительно через PyCryptodome в тестах.
В рабочем коде EVP и готовый режим GCM не используются — только AES-ECB
как блочный примитив. Фактические результаты приведены в [TESTING.md](TESTING.md).

## Хеширование файлов

Подкоманда `dgst` поддерживает две собственные потоковые реализации:

- `sha256` — SHA-256 по NIST FIPS 180-4, конструкция Merkle–Damgård с
  512-битными блоками и 256-битным результатом;
- `sha3-256` — SHA3-256 по NIST FIPS 202, губчатая конструкция на основе
  перестановки Keccak-f[1600] с 1088-битной скоростью и 256-битным результатом.

Обе функции реализованы без `hashlib` и других готовых реализаций хешей.
Файлы читаются в бинарном режиме блоками по 8192 байта, поэтому потребление
памяти не зависит от размера файла. Результат состоит из 64 hex-символов
нижнего регистра.

SHA-256:

```powershell
cryptocore dgst --algorithm sha256 --input document.pdf
```

SHA3-256:

```powershell
cryptocore dgst --algorithm sha3-256 --input archive.zip
```

Формат stdout совместим с утилитами семейства `*sum`:

```text
HASH_VALUE  INPUT_FILE_PATH
```

Запись той же строки в файл вместо stdout:

```powershell
cryptocore dgst --algorithm sha256 --input document.pdf --output document.sha256
```

Поддерживается двоичный стандартный ввод; `-` сохраняется как имя источника:

```bash
printf "abc" | cryptocore dgst --algorithm sha256 --input -
```

Хеш-функция позволяет обнаружить случайное изменение данных, но сама по себе
не подтверждает отправителя и не защищает от намеренной подмены вместе с
хешем. Для аутентичности нужен MAC, уже используемый в `cbc-hmac` и `ctr-hmac`.
SHA-256 и SHA3-256 считаются стойкими к практическому поиску коллизий на
текущем уровне знаний; новые системы могут предпочитать SHA3-256 из-за иной
внутренней конструкции. MD5 и SHA-1 намеренно не поддерживаются.

## HMAC: подлинность и целостность файлов (спринт 5)

Команда `dgst --hmac` вычисляет HMAC-SHA256 на основе собственной реализации
SHA-256. Файлы читаются в бинарном режиме фрагментами по 8192 байта: весь
файл не накапливается в памяти. Готовые реализации HMAC и `hashlib` не
используются для вычисления тега в основном коде.

Параметры:

- `--hmac` — включить HMAC-SHA256;
- `--key KEY` — обязательный секретный ключ в hex; допускается произвольная
  длина в байтах, а не только 16 байт, как у AES. Строка должна содержать
  чётное число hex-символов без пробелов;
- `--algorithm sha256` — базовый алгоритм. С `--hmac` его можно опустить:
  выбирается SHA-256. SHA3-256 для HMAC в этом спринте не поддерживается;
- `--input FILE` — входной файл, либо `-` для двоичного стандартного ввода;
- `--output FILE` — сохранить тег вместо вывода в консоль;
- `--verify FILE` — сравнить вычисленный тег с ожидаемым; эта опция
  несовместима с `--output` и не изменяет файлы.

Генерация HMAC (ключ в примере учебный, не используйте его для реальных данных):

```powershell
cryptocore dgst --algorithm sha256 --hmac --key 00112233445566778899aabbccddeeff --input message.txt
cryptocore dgst --algorithm sha256 --hmac --key 00112233445566778899aabbccddeeff --input message.txt --output message.hmac
```

Формат вывода: полный 256-битный тег, один пробел и путь к входному файлу:

```text
HMAC_VALUE INPUT_FILE_PATH
```

Проверка ранее сохранённого HMAC:

```powershell
cryptocore dgst --algorithm sha256 --hmac --key 00112233445566778899aabbccddeeff --input message.txt --verify message.hmac
# [OK] Проверка HMAC пройдена
$LASTEXITCODE
# 0
```

После изменения одного байта файла или применения другого ключа команда
сообщит: `проверка HMAC не пройдена: неверный ключ или изменённые данные`.
Код завершения — `1`. Ошибки аргументов дают код `2`; некорректный или
недоступный файл ожидаемого тега — код `1`. Причина несовпадения не различается.

Файл для `--verify` должен содержать одну непустую строку: 64 hex-символа,
затем необязательное имя файла. Регистр hex, начальные/конечные пробелы,
пустые строки и UTF-8 BOM допускаются. Имя файла игнорируется: проверяется
именно файл из `--input`, а не путь из файла с тегом. Несколько тегов,
неполные теги и неверный hex отклоняются. Размер файла ожидаемого тега
ограничен 65536 символами.

Проверка стандартного ввода в Linux/WSL:

```bash
printf "abc" | cryptocore dgst --hmac --key 00112233445566778899aabbccddeeff --input - --output stdin.hmac
printf "abc" | cryptocore dgst --hmac --key 00112233445566778899aabbccddeeff --input - --verify stdin.hmac
```

### Конструкция и ограничения безопасности

Реализация следует [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104):

```text
HMAC(K, m) = SHA256((K' XOR opad) || SHA256((K' XOR ipad) || m))
```

Ключ длиннее 64 байт сначала хешируется SHA-256. После этого ключ дополняется
нулями до 64 байт. `ipad` — 64 байта `0x36`, `opad` — 64 байта `0x5c`.
Потоковый API `HMAC.update()` позволяет добавлять фрагменты; `digest()` и
`hexdigest()` не изменяют состояние. `compute(message)` вычисляет тег
отдельного сообщения с тем же ключом. Внутренние защищённые режимы используют
тот же модуль HMAC, без второй копии реализации.

HMAC подтверждает целостность и владение общим секретным ключом, но не шифрует
данные и не является цифровой подписью: любой владелец ключа может создать тег.
Имя файла не входит в тег. Повторная передача старой пары «файл + тег» также
не предотвращается автоматически. Ключ нужно передавать отдельно по защищённому
каналу и сохранять в секрете. RFC 2104 рекомендует случайный ключ не короче
длины хеша — для SHA-256 это 32 байта. Пустые и короткие ключи математически
поддерживаются, но не рекомендуются для защиты данных.

`--key` может попасть в историю оболочки и список аргументов процесса.
Не публикуйте реальные ключи в репозитории или отчётах. `--key-file` из
шифрования пока не распространяется на `dgst`: у AES и HMAC разные требования
к длине ключа. Сравнение полных тегов использует `compare_digest`, а не
обычное посимвольное сравнение; это не означает строгий constant-time для
всей учебной реализации Python. Бонус AES-CMAC реализован в версии 0.6.1
и описан в следующем разделе.

## AES-CMAC: дополнение пятого спринта

Закрыты замечания преподавателя: **CLI-5** (`--cmac`), **MAC-6**
(собственная реализация AES-CMAC) и **TEST-8** (опубликованные векторы NIST).
Реализован AES-128-CMAC по
[NIST SP 800-38B](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-38B.pdf),
с тем же примитивом AES, который использовался в предыдущих спринтах.
Готовый CMAC библиотеки применяется только в тестах как независимый эталон.

### CLI: генерация и проверка

```powershell
cryptocore dgst --algorithm aes --cmac --key 2b7e151628aed2a6abf7158809cf4f3c --input message.txt
cryptocore dgst --algorithm aes --cmac --key 2b7e151628aed2a6abf7158809cf4f3c --input message.txt --output message.cmac
cryptocore dgst --algorithm aes --cmac --key 2b7e151628aed2a6abf7158809cf4f3c --input message.txt --verify message.cmac
# [OK] Проверка CMAC пройдена
```

Ключ в примере опубликован NIST и пригоден только для тестов. Для своих
данных нужен отдельный случайный секретный ключ, не используемый для
шифрования, GCM, HMAC или других протоколов.

- `--cmac` и `--hmac` взаимоисключающие;
- `--key` обязателен: ровно 32 hex-символа, то есть 16 байт для AES-128.
  Ключи AES-192/256 в этой версии проекта не поддерживаются;
- `--algorithm aes` можно опустить при `--cmac`; хеш-алгоритмы SHA для
  CMAC не принимаются. Для HMAC по-прежнему используется `sha256` и ключ
  произвольной длины;
- формат результата — `CMAC_VALUE INPUT_FILE_PATH`, один пробел между
  полным 128-битным тегом (32 hex-символа) и именем файла;
- `--input -` обрабатывает двоичный стандартный ввод; `--output` сохраняет
  ту же строку в UTF-8 без вывода тега в консоль;
- `--verify` читает один полный тег, допускает пробелы, верхний регистр,
  UTF-8 BOM и необязательное имя файла. Проверяется файл из `--input`,
  имя в строке с тегом игнорируется. Усечённые теги и 64-символьные
  HMAC-теги не принимаются за CMAC;
- успех проверки — код `0`, неверный ключ/изменённые данные/тег — код `1`,
  неверные аргументы — код `2`. `--verify` несовместим с `--output`.

Проверка стандартного ввода в Linux/WSL:

```bash
printf 'abc' | cryptocore dgst --cmac --key 2b7e151628aed2a6abf7158809cf4f3c --input - --output stdin.cmac
printf 'abc' | cryptocore dgst --cmac --key 2b7e151628aed2a6abf7158809cf4f3c --input - --verify stdin.cmac
```

### Конструкция и потоковый API

Подключи получаются из `L = AES_K(0^128)`: `K1` — сдвиг L влево на один
бит с условным XOR `Rb = 0x87`, `K2` — такая же операция над K1.
Полные промежуточные блоки обрабатываются как CBC-MAC с нулевым начальным
состоянием. Полный последний блок маскируется K1; неполный или пустой —
дополняется `0x80` и нулями, затем маскируется K2. После финального AES
возвращается весь 16-байтный тег. PKCS#7 здесь не применяется.

Файлы читаются по 8192 байта. Объект хранит CBC-состояние и не более
16 байт последнего блока; размер файла не определяет потребление памяти.
`digest()`/`hexdigest()` не изменяют состояние, дальнейший `update()`
допустим. `compute(message)` вычисляет тег отдельного сообщения с тем же ключом.

```python
from pathlib import Path
from cryptocore import CMAC, cmac_aes, cmac_file

key = bytes.fromhex("2b7e151628aed2a6abf7158809cf4f3c")  # Только тестовый ключ NIST.
mac = CMAC(key)
mac.update(b"first ").update(b"second")
assert mac.digest() == cmac_aes(key, b"first second")
tag_hex = cmac_file(Path("message.txt"), key)
```

Для файлового API путь передаётся объектом `Path`, например
`cmac_file(Path("message.txt"), key)` после `from pathlib import Path`.
Для бинарных потоков доступен `cmac_stream(stream, key)`.
CMAC подтверждает целостность и владение общим ключом, но не шифрует
сообщение, не является цифровой подписью и сам по себе не блокирует replay.
Имя файла не включается в тег. Сравнение полных тегов выполняется через
`compare_digest`; гарантия constant-time для всего Python-кода не заявляется.
Ключ из `--key` может быть виден в истории оболочки и аргументах процесса;
реальные ключи не следует публиковать. `--key-file` в `dgst` пока не поддерживается.

Проверяются подключи K1/K2 и все четыре опубликованных примера

при попытке чтения целиком. Результаты приведены в [TESTING.md](TESTING.md).

## Получение ключей: PBKDF2 и иерархия (спринт 7)

Команда `derive` реализует PBKDF2-HMAC-SHA256 по RFC 2898 / RFC 8018.
PBKDF2, HMAC и SHA-256 вычисляются собственным кодом Python: готовые KDF,
`hashlib` и библиотечный HMAC в рабочем алгоритме не используются.
PBKDF2 растягивает пароль за счёт повторных вычислений, повышая стоимость
каждой попытки перебора, но не делает слабый пароль автоматически сильным.

### CLI

```powershell
cryptocore derive --algorithm pbkdf2 --password 'Учебный пароль!' --salt 000102030405060708090a0b0c0d0e0f --iterations 100000 --length 32
```

Кавычки защищают пробелы и специальные символы оболочки. Пароль в примерах
учебный; реальные пароли не следует записывать в историю команд или Git.

Параметры:

- `--algorithm pbkdf2` — единственный алгоритм CLI, также выбран по умолчанию;
- ровно один источник пароля: `--password PASSWORD`, `--password-file FILE`
  либо `--password-env NAME`;
- `--salt HEX` — строгая hex-строка чётной длины без пробелов и `0x`.
  Если опция отсутствует, CSPRNG генерирует новый случайный salt длиной 16 байт;
- `--iterations COUNT` — положительное целое число, по умолчанию 100000
  согласно заданию; значения от 1 сохраняются для тестовых векторов;
- `--length LENGTH` — длина результата в байтах, по умолчанию 32;
- `--output FILE` — дополнительно сохранить ключ в новый защищённый файл
  как **сырые бинарные байты**, без hex, salt и перевода строки.

Стандартный вывод всегда имеет формат:

```text
KEY_HEX  SALT_HEX
```

Между значениями ровно два пробела. Например, для известного тестового ввода:

```powershell
cryptocore derive --password 'password' --salt 73616c74 --iterations 1 --length 32
# 120fb6cffcf8b32c43e7225256c4f837a86548c92ccc35480805987cb70be17b  73616c74
```

Предупреждения о числе итераций ниже учебного значения 100000 и salt короче
16 байт идут только в stderr и не нарушают формат stdout. Оба параметра
показанного тестового вектора не подходят для защиты реальных данных.

Генерация случайного salt и бинарного ключа:

```powershell
cryptocore derive --password 'Учебный пароль!' --iterations 100000 --length 32 --output derived.key
```

Даже при `--output` строка `KEY_HEX  SALT_HEX` остаётся в stdout по контракту
CLI. Она содержит секретный ключ: не отправляйте её в общедоступные логи.
В бинарный файл salt не записывается. Сохраните salt, число итераций, длину
и алгоритм отдельно: те же пароль и параметры нужны для воспроизведения ключа.
Salt не является секретом и препятствует общей предвычисленной атаке на
разные пароли; для нового получения ключа используйте новый случайный salt.

Файл `--output` создаётся с правами 0600 в Linux/WSL. На Windows наследование
ACL отключается до записи секрета и доступ остаётся текущему пользователю.
Существующие файлы и ссылки не перезаписываются; при отказе установки прав
ключ не записывается. Файлы `*.key` исключены из Git.

**Форматы различаются:** `derive --output` выдаёт бинарный ключ произвольной
длины, а `--key-file` команды шифрования по-прежнему принимает hex-ключ
AES-128 (32 символа). Бинарный `derived.key` нельзя напрямую передать в
этот `--key-file`. Для AES нужен ключ длиной 16 байт; используйте KEY_HEX
из stdout с `--key` либо байты ключа через библиотечный API.

### Пароль из файла или окружения

```powershell
cryptocore derive --password-file password.bin --iterations 100000 --length 32
cryptocore derive --password-env CRYPTOCORE_PASSWORD --iterations 100000 --length 32
```

Для `--password-env` переменная `CRYPTOCORE_PASSWORD` должна быть заранее
задана доверенным способом. Программа не меняет и не удаляет её. Отсутствие
переменной или файла — ошибка с кодом 1, без вывода ключа. Строковые пароли
из аргумента и окружения кодируются UTF-8, без нормализации и обрезания пробелов.

`--password-file` читает точные бинарные байты: BOM, NUL и завершающие
`LF`/`CRLF` входят в пароль. Обычный `echo` может добавить перевод строки
и тем самым изменить пароль. Ограничьте доступ к исходному файлу сами
(например, `chmod 600 password.bin` в Linux); программа не меняет его права.

После использования изменяемый буфер пароля перезаписывается, ссылки на
пароль в разобранных аргументах снимаются. **Гарантии полного стирания нет:**
строки Python, временные копии, `sys.argv`, окружение и состояние HMAC могут
оставаться в памяти. Варианты file/env уменьшают передачу пароля в аргументах,
но не защищают от доступа к процессу с теми же/повышенными правами.

### Алгоритм и иерархия ключей

Для каждого блока PBKDF2 вычисляется `U1 = HMAC(P, salt || INT_32_BE(i))`,
затем `Uj = HMAC(P, Uj-1)`. Результаты U объединяются XOR; блоки результата
конкатенируются и обрезаются точно до нужной длины. Поддерживаются пустые,
длинные и бинарные пароли/salt, а также результат длиннее одного 32-байтного
блока. API принимает salt как байты; строка пароля дополнительно может быть
UTF-8-текстом. Форматный предел длины — `(2^32 - 1) * 32` байт, практический
ограничен памятью и временем вычисления. Boolean вместо числа не принимается.

HMAC сохраняет начальные состояния SHA-256 после ipad/opad и копирует их
для повторных сообщений. Для 32-байтных U требуется две функции сжатия
SHA-256 вместо повторной обработки ключа на каждой итерации. Оптимизация
проверена на прежних векторах SHA/HMAC и не меняет форматы файлов.

```python
from cryptocore import pbkdf2_hmac_sha256, derive_key, generate_random_bytes

salt = generate_random_bytes(16)  # Сохранить вместе с параметрами, не как часть ключа.
master = pbkdf2_hmac_sha256("Учебный пароль!", salt, iterations=100000, dklen=32)
encryption_key = derive_key(master, "app/v1/encryption", 16)
authentication_key = derive_key(master, "app/v1/authentication", 32)
assert encryption_key != authentication_key[:16]
```

`derive_key(master_key: bytes, context: str, length: int = 32)` использует
ровно формулу задания: `HMAC(master_key, UTF8(context) || INT_32_BE(counter))`
для счётчиков от 1, затем конкатенацию и обрезание. Контекст — непустой,
регистрозависимый идентификатор назначения; master key тоже непустой.
Это не парольный KDF: master key должен быть уже качественным секретом.
Одинаковые входы дают тот же результат, разные контексты разделяют назначения;
короткий результат является префиксом длинного для того же контекста.

Модуль `kdf/hkdf.py` назван по структуре задания, но функция является
упрощённой HMAC-иерархией, **не HKDF-Extract/Expand из RFC 5869**.
Существующие derivation-форматы CBC-HMAC/CTR-HMAC/EtM не заменяются,
поэтому совместимость ранее зашифрованных файлов сохраняется.

### Неточности примеров задания и рекомендации

[RFC 6070](https://www.rfc-editor.org/rfc/rfc6070) содержит векторы
PBKDF2-HMAC-SHA1, а не SHA256. Например, `0c60c80f...` из задания — результат
SHA1, который не должен получаться у правильной SHA256-реализации.
Используются оба SHA256-вектора раздела 11
[RFC 7914](https://www.rfc-editor.org/rfc/rfc7914#section-11), входы RFC 6070
с независимым пересчётом на SHA256 и проверки `hashlib`/OpenSSL.
SHA1 не добавлен вместо требуемого SHA256.

Строка `fixedappsalt` из примера задания не является hex и отклоняется.
В OpenSSL для тех же байтов нужно указывать `hexsalt:...`, а не `salt:...`,
и явно выбирать `digest:SHA256`. Форматы stdout двух программ отличаются:
в тестах сравниваются байты ключа, а не полные текстовые строки.

Значение 100000 по умолчанию сохранено как учебное требование, а не как
современный производственный минимум. На дату проверки
[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
рекомендует для PBKDF2-HMAC-SHA256 600000 итераций. Для реальной системы
используйте проверенную библиотеку, актуальные параметры и измерение на
целевой машине: медленный Python-код проекта не замедляет быстрые реализации
перебора у атакующего. Сильный пароль и уникальный случайный salt необходимы.

## Тестирование

### Режимы и IV (спринт 2)

Параметр `--mode` принимает `ecb`, `cbc`, `cfb`, `ofb`, `ctr`.
ECB и CBC используют PKCS#7, включая дополнительный блок для данных кратной
16 байтам длины. CFB (сегмент 128 бит), OFB и CTR не используют дополнение
и сохраняют длину данных, включая пустые файлы и неполные последние блоки.
Старый CTR использует весь 16-байтный IV как счётчик big-endian. При нехватке
оставшихся значений операция завершается ошибкой до шифрования: перенос между
байтами разрешён, числовое переполнение 128-битного слова запрещено.

Для новых режимов при шифровании IV генерируется через выделенную функцию
`generate_random_bytes(16)`, которая использует `os.urandom(16)`.
Формат результата: `[16 байт IV][шифротекст]`. Ключ в файл не записывается.
При расшифровании без `--iv` заголовок извлекается автоматически.
При явном `--iv` весь входной файл считается шифротекстом **без заголовка**,
как в выводе OpenSSL. IV — ровно 32 hex-символа.
Передача `--iv` при шифровании или в режиме ECB считается ошибкой.

Пример PowerShell (замените `cbc` на любой другой новый режим):

```powershell
cryptocore --algorithm aes --mode cbc --encrypt --key 000102030405060708090a0b0c0d0e0f --input original.txt --output encrypted.bin
cryptocore --algorithm aes --mode cbc --decrypt --key 000102030405060708090a0b0c0d0e0f --input encrypted.bin --output decrypted.txt
fc.exe /b original.txt decrypted.txt
```

Для файла от OpenSSL:

```powershell
cryptocore --algorithm aes --mode cbc --decrypt --key 000102030405060708090a0b0c0d0e0f --iv 000102030405060708090a0b0c0d0e0f --input openssl.bin --output decrypted.txt
```

Эти режимы не обеспечивают аутентификацию: неверный ключ или изменение
шифротекста не всегда обнаруживаются. Проверка padding не заменяет MAC.

### Ручной приёмочный тест

```bash
printf "Проверка CryptoCore" > original.txt
cryptocore --algorithm aes --mode ecb --encrypt --key 000102030405060708090a0b0c0d0e0f --input original.txt --output encrypted.bin
cryptocore --algorithm aes --mode ecb --decrypt --key 000102030405060708090a0b0c0d0e0f --input encrypted.bin --output decrypted.txt
cmp original.txt decrypted.txt
```

В Windows сравнить файлы побайтово можно так:

```powershell
fc.exe /b original.txt decrypted.txt
```

Отсутствие вывода `cmp` или сообщение `FC: no differences encountered`
означает, что файлы совпадают.

### Проверка совместимости с OpenSSL

Полный сценарий второго спринта проверяет CBC, CFB-128, OFB и CTR в обе стороны:
CryptoCore → OpenSSL и OpenSSL → CryptoCore. Он запускает CLI как отдельные
процессы для 9 размеров данных, извлекает IV из заголовка и сравнивает байты.
Временные файлы создаются в отдельном каталоге и автоматически удаляются.

```powershell
python -m unittest tests.test_modes.OpenSSLTests -v
```

OpenSSL ищется в PATH и в `C:/Program Files/Git/usr/bin/openssl.exe`.
Другой путь можно задать в PowerShell:

```powershell
$env:OPENSSL = "C:\Program Files\Git\usr\bin\openssl.exe"
python -m unittest tests.test_modes.OpenSSLTests -v
```

Если OpenSSL отсутствует, тест отмечается как пропущенный (`skipped`).
Для приёмки совместимости требуется успешный запуск без пропуска.

CryptoCore использует стандартное дополнение PKCS#7, соответствующее поведению
`openssl enc` по умолчанию:

```bash
openssl enc -aes-128-ecb -K 000102030405060708090a0b0c0d0e0f -in plaintext.txt -out openssl.bin
cryptocore --algorithm aes --mode ecb --decrypt --key 000102030405060708090a0b0c0d0e0f --input openssl.bin --output openssl-decrypted.txt
cmp plaintext.txt openssl-decrypted.txt
```

# CryptoCore

CryptoCore — минималистический консольный криптографический провайдер для
шифрования и расшифрования файлов с помощью AES-128, а также вычисления
SHA-256 и SHA3-256. Реализованы первые четыре спринта.
Дополнительно внесены замечания преподавателя к третьему спринту:
аутентифицированные форматы, защищённые ключевые файлы и контроль CTR.

> **Предупреждение о безопасности:** режим ECB раскрывает повторяющиеся шаблоны
> открытого текста и не подходит для защиты реальных данных. В этом проекте он
> реализован исключительно как учебная основа для более безопасных режимов из
> следующих спринтов.

## Требования

- Python 3.9 или новее;
- `pip`;
- [PyCryptodome](https://pycryptodome.readthedocs.io/) версии 3.20 или новее.

PyCryptodome предоставляет проверенный блочный примитив AES. CryptoCore
самостоятельно реализует логику режимов, GHASH для GCM, HMAC-SHA256 и PKCS#7.

## Установка

Создайте изолированное окружение и установите проект из его корневого каталога.

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip

```

### Linux и macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip

```

После установки проверьте доступность консольной команды:

```bash

```

```bash
cryptocore dgst --help
```

## Использование

Ключ передаётся в виде ровно 32 шестнадцатеричных символов — это 16 байт,
необходимые для AES-128. При шифровании `--key` можно не указывать: CryptoCore
сгенерирует ключ системным CSPRNG и один раз выведет его в `stdout`.

Шифрование файла:

```bash
cryptocore --algorithm aes --mode ecb --encrypt \
  --key 000102030405060708090a0b0c0d0e0f \
  --input plaintext.txt --output ciphertext.bin
```

Шифрование с автоматической генерацией ключа:

```bash
cryptocore --algorithm aes --mode ctr --encrypt \
  --input plaintext.txt --output ciphertext.bin
# [ИНФО] Сгенерирован случайный ключ: <32 hex-символа>
```

Сохраните показанный ключ: он намеренно не записывается в файл с шифротекстом.
Без него расшифрование невозможно. Для расшифрования обязательно указать
`--key` либо `--key-file`. При ключе из одинаковых или последовательных байтов программа
выводит предупреждение в `stderr`.

Расшифрование файла:

```bash
cryptocore --algorithm aes --mode ecb --decrypt \
  --key 000102030405060708090a0b0c0d0e0f \
  --input ciphertext.bin --output decrypted.txt
```

Параметры `--algorithm aes`, `--mode` и `--input` обязательны.
Также необходимо указать ровно один из флагов: `--encrypt` или `--decrypt`.
Если параметр `--output` отсутствует, CryptoCore добавляет к имени входного
файла расширение `.enc` при шифровании или `.dec` при расшифровании.

Ошибки аргументов, файловой системы и криптографических операций выводятся в
стандартный поток ошибок. При ошибке программа завершается с ненулевым кодом.

## Аутентифицированное шифрование и ключевые файлы

Для новых файлов доступны `gcm`, `cbc-hmac` и `ctr-hmac`. При неверном ключе,
AAD или изменении данных команда возвращает общую ошибку аутентификации.
Проверка тега предшествует расшифрованию: выходной файл не создаётся, а
существующий файл не изменяется при отказе.

Пример GCM с новым ключом в отдельном защищённом файле:

```powershell
cryptocore --algorithm aes --mode gcm --encrypt --input document.pdf --output document.gcm --save-key document.key --aad aabb
cryptocore --algorithm aes --mode gcm --decrypt --input document.gcm --output restored.pdf --key-file document.key --aad aabb
```

`--save-key` разрешён только при генерации нового ключа во время шифрования.
Файл содержит 32 hex-символа и перевод строки; существующие файлы и ссылки
не перезаписываются. В этом случае ключ не выводится в stdout. Без этой
опции вывод нового ключа остаётся прежним.

В Linux/WSL файл создаётся с правами **0600**. На Windows до записи ключа
отключается наследование ACL и доступ предоставляется только текущему
пользователю через `icacls`; при отказе ограничения прав ключ не записывается.
При чтении в Linux отклоняются ключевые файлы с доступом для группы/остальных
пользователей. Символические ссылки отклоняются. Для самостоятельно созданных
ключевых файлов Windows ограничение ACL следует установить отдельно.
Ключевой файл нельзя перезаписать выходным файлом шифрования, включая жёсткие
ссылки. `*.key` исключены из Git.

`--key` и `--key-file` взаимоисключающие. Файловая передача позволяет не
размещать ключ в аргументах процесса и истории команд. Для работы без вывода
ключа используйте `--save-key`, затем `--key-file`.

| Режим | Формат файла |
| --- | --- |
| `gcm` | `nonce (12 байт) ∥ ciphertext ∥ tag (16 байт)` |
| `cbc-hmac` | `CCBC\x01 ∥ IV (16 байт) ∥ ciphertext ∥ HMAC (32 байта)` |
| `ctr-hmac` | `CCTR\x01 ∥ размер сегмента (4 байта) ∥ длина данных (8 байт) ∥ HMAC заголовка (32 байта) ∥ сегменты` |

GCM реализован по [NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf).
CBC-HMAC и CTR-HMAC используют собственные версионированные форматы.
Разные ключи AES и MAC выводятся из основного ключа через HMAC-SHA256 с
метками назначения и формата. Каждый MAC включает длину AAD и сами AAD.
CBC-HMAC аутентифицирует версию, IV и шифротекст до CBC и проверки padding.

В CTR-HMAC сегмент состоит из nonce (12 байт), шифротекста и HMAC (32 байта).
Тег связывает заголовок, номер сегмента, nonce и шифротекст: перестановка,
усечение и дописывание сегментов обнаруживаются. Все теги проверяются до
расшифрования. Целые числа в заголовке записываются big-endian.

`--aad` принимает hex-строку и разрешён только для трёх аутентифицированных
режимов. Он не записывается в файл; при расшифровании нужно повторить то же
значение. Для GCM-файла без заголовка можно передать nonce через `--nonce`
либо `--iv` при расшифровании; файл должен включать тег. При шифровании
nonce/IV всегда генерируется автоматически.

В CTR-HMAC 96-битный nonce отделён от 32-битного счётчика, начинающегося с
нуля для каждого сегмента. Nonce обновляется каждый 1 МиБ по умолчанию;
допустимый размер сегмента — от 1 байта до 64 МиБ:

```powershell
cryptocore --algorithm aes --mode ctr-hmac --encrypt --input archive.zip --output archive.ctr --save-key archive.key --ctr-segment-size 1048576
cryptocore --algorithm aes --mode ctr-hmac --decrypt --input archive.ctr --output restored.zip --key-file archive.key
```

Все nonce создаются CSPRNG. Повтор внутри файла приводит к повторной генерации
и отказу после восьми неудачных попыток. Предел счётчика проверяется заранее.
Между файлами уникальность случайных nonce вероятностная; для больших серий
операций необходимо также менять ключи. Для GCM используйте отдельный ключ,
который не используется в других режимах; nonce не должен повторяться с ним.

Старые форматы сохраняются для совместимости. В старом CTR теперь запрещено
числовое переполнение счётчика. Переход на `ctr-hmac` требует повторного
шифрования исходного файла.

PKCS#7 проверяет все 16 байтов последнего блока без ранних выходов по содержимому.
**Строгое constant-time исполнение Python не гарантируется.** Обычный CBC без
MAC не защищён от padding oracle; защиту обеспечивает `cbc-hmac` с проверкой
MAC до CBC и unpad. Тесты проверяют этот порядок, а не доказывают отсутствие
всех побочных каналов интерпретатора.

Ротация nonce ограничивает использование счётчика. Операции шифрования пока
загружают весь файл в память; постоянное потребление памяти реализовано для `dgst`.

## Хеширование файлов

Подкоманда `dgst` поддерживает две собственные потоковые реализации:

- `sha256` — SHA-256 по NIST FIPS 180-4, конструкция Merkle–Damgård с
  512-битными блоками и 256-битным результатом;
- `sha3-256` — SHA3-256 по NIST FIPS 202, губчатая конструкция на основе
  перестановки Keccak-f[1600] с 1088-битной скоростью и 256-битным результатом.

Обе функции реализованы без `hashlib` и других готовых реализаций хешей.
Файлы читаются в бинарном режиме блоками по 8192 байта, поэтому потребление
памяти не зависит от размера файла. Результат состоит из 64 hex-символов
нижнего регистра.

SHA-256:

```powershell
cryptocore dgst --algorithm sha256 --input document.pdf
```

SHA3-256:

```powershell
cryptocore dgst --algorithm sha3-256 --input archive.zip
```

Формат stdout совместим с утилитами семейства `*sum`:

```text
HASH_VALUE  INPUT_FILE_PATH
```

Запись той же строки в файл вместо stdout:

```powershell
cryptocore dgst --algorithm sha256 --input document.pdf --output document.sha256
```

Поддерживается двоичный стандартный ввод; `-` сохраняется как имя источника:

```bash
printf "abc" | cryptocore dgst --algorithm sha256 --input -
```

Хеш-функция позволяет обнаружить случайное изменение данных, но сама по себе
не подтверждает отправителя и не защищает от намеренной подмены вместе с
хешем. Для аутентичности нужен MAC, уже используемый в `cbc-hmac` и `ctr-hmac`.
SHA-256 и SHA3-256 считаются стойкими к практическому поиску коллизий на
текущем уровне знаний; новые системы могут предпочитать SHA3-256 из-за иной
внутренней конструкции. MD5 и SHA-1 намеренно не поддерживаются.

## Тестирование

### Режимы и IV (спринт 2)

Параметр `--mode` принимает `ecb`, `cbc`, `cfb`, `ofb`, `ctr`.
ECB и CBC используют PKCS#7, включая дополнительный блок для данных кратной
16 байтам длины. CFB (сегмент 128 бит), OFB и CTR не используют дополнение
и сохраняют длину данных, включая пустые файлы и неполные последние блоки.
Старый CTR использует весь 16-байтный IV как счётчик big-endian. При нехватке
оставшихся значений операция завершается ошибкой до шифрования: перенос между
байтами разрешён, числовое переполнение 128-битного слова запрещено.

Для новых режимов при шифровании IV генерируется через выделенную функцию
`generate_random_bytes(16)`, которая использует `os.urandom(16)`.
Формат результата: `[16 байт IV][шифротекст]`. Ключ в файл не записывается.
При расшифровании без `--iv` заголовок извлекается автоматически.
При явном `--iv` весь входной файл считается шифротекстом **без заголовка**,
как в выводе OpenSSL. IV — ровно 32 hex-символа.
Передача `--iv` при шифровании или в режиме ECB считается ошибкой.

Пример PowerShell (замените `cbc` на любой другой новый режим):

```powershell
cryptocore --algorithm aes --mode cbc --encrypt --key 000102030405060708090a0b0c0d0e0f --input original.txt --output encrypted.bin
cryptocore --algorithm aes --mode cbc --decrypt --key 000102030405060708090a0b0c0d0e0f --input encrypted.bin --output decrypted.txt
fc.exe /b original.txt decrypted.txt
```

Для файла от OpenSSL:

```powershell
cryptocore --algorithm aes --mode cbc --decrypt --key 000102030405060708090a0b0c0d0e0f --iv 000102030405060708090a0b0c0d0e0f --input openssl.bin --output decrypted.txt
```

Эти режимы не обеспечивают аутентификацию: неверный ключ или изменение
шифротекста не всегда обнаруживаются. Проверка padding не заменяет MAC.

После установки запустите полный набор тестов из корневого каталога проекта:

```bash
python -m unittest discover -s tests -v
```

сообщения, `abc`, многоблочного сообщения и миллиона символов `a`; границы

потоковое чтение и виртуальный файл размером больше 1 ГиБ; CLI и совместимость
обоих алгоритмов с OpenSSL. Дополнительные тесты проверяют AEAD, padding oracle,
CTR, ключевые файлы и статистику распределения байтов. Полный набор содержит
76 тестов, включая платформенные проверки Windows и Linux/WSL.

Отдельно запустить тесты хеширования можно так:

```powershell
python -m unittest tests.test_hashes tests.test_digest_cli -v
```

Ручная сверка SHA-256 в Linux/WSL:

```bash
cryptocore dgst --algorithm sha256 --input document.pdf
sha256sum document.pdf
```

Ручная сверка SHA3-256 через OpenSSL:

```bash
cryptocore dgst --algorithm sha3-256 --input document.pdf
openssl dgst -sha3-256 document.pdf
```

Проверки CSPRNG и инструкция по батарее NIST SP 800-22 приведены в
[TESTING.md](TESTING.md). Краткий запуск:

```powershell
python -m pip install -e ".[nist]"
python scripts/generate_nist_data.py --size 137500
python scripts/run_nist_tests.py nist_test_data.bin
```

Тесты проверяют пустые, короткие, выровненные по размеру блока, многоблочные и
двоичные входные данные; опубликованный тестовый вектор AES; работу PKCS#7;
неправильные ключи, шифротекст и дополнение; файловые ошибки; автоматическое
имя выходного файла и полный цикл обработки файла.

### Ручной приёмочный тест

```bash
printf "Проверка CryptoCore" > original.txt
cryptocore --algorithm aes --mode ecb --encrypt --key 000102030405060708090a0b0c0d0e0f --input original.txt --output encrypted.bin
cryptocore --algorithm aes --mode ecb --decrypt --key 000102030405060708090a0b0c0d0e0f --input encrypted.bin --output decrypted.txt
cmp original.txt decrypted.txt
```

В Windows сравнить файлы побайтово можно так:

```powershell
fc.exe /b original.txt decrypted.txt
```

Отсутствие вывода `cmp` или сообщение `FC: no differences encountered`
означает, что файлы совпадают.

### Проверка совместимости с OpenSSL

Полный сценарий второго спринта проверяет CBC, CFB-128, OFB и CTR в обе стороны:
CryptoCore → OpenSSL и OpenSSL → CryptoCore. Он запускает CLI как отдельные
процессы для 9 размеров данных, извлекает IV из заголовка и сравнивает байты.
Временные файлы создаются в отдельном каталоге и автоматически удаляются.

```powershell
python -m unittest tests.test_modes.OpenSSLTests -v
```

OpenSSL ищется в PATH и в `C:/Program Files/Git/usr/bin/openssl.exe`.
Другой путь можно задать в PowerShell:

```powershell
$env:OPENSSL = "C:\Program Files\Git\usr\bin\openssl.exe"
python -m unittest tests.test_modes.OpenSSLTests -v
```

Если OpenSSL отсутствует, тест отмечается как пропущенный (`skipped`).
Для приёмки совместимости требуется успешный запуск без пропуска.

CryptoCore использует стандартное дополнение PKCS#7, соответствующее поведению
`openssl enc` по умолчанию:

```bash
openssl enc -aes-128-ecb -K 000102030405060708090a0b0c0d0e0f -in plaintext.txt -out openssl.bin
cryptocore --algorithm aes --mode ecb --decrypt --key 000102030405060708090a0b0c0d0e0f --input openssl.bin --output openssl-decrypted.txt
cmp plaintext.txt openssl-decrypted.txt
```

## Структура проекта

```text
src/cryptocore/
├── cli.py          # разбор аргументов и управление выполнением команды
├── csprng.py       # системный CSPRNG для ключей и IV
├── authentication.py # HMAC-SHA256 и разделение ключей
├── key_files.py    # ключевые файлы, 0600 и Windows ACL
├── file_io.py      # двоичные файловые операции
├── errors.py       # прикладные ошибки для вывода пользователю
├── hashes/
│   ├── file_hash.py # потоковое чтение и хеширование файлов
│   ├── sha256.py    # собственная реализация SHA-256
│   └── sha3_256.py  # собственная реализация SHA3-256/Keccak
└── modes/
    ├── ecb.py      # AES-128 ECB и PKCS#7
    ├── feedback.py # CBC, CFB-128, OFB и CTR
    ├── gcm.py      # собственные GCM и GHASH
    └── authenticated.py # CBC-HMAC и CTR-HMAC с ротацией nonce
tests/              # модульные и интеграционные тесты
scripts/            # подготовка данных и запуск батареи NIST
TESTING.md          # процедура и результаты статистических тестов
pyproject.toml      # конфигурация пакета, зависимостей и консольной команды
```
